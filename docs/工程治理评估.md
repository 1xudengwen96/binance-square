# 工程治理评估：AI 知识、数据生命周期与数据库

评估日期：2026-10-21。依据当前仓库源码、部署配置、现有文档，以及 SQLite、PostgreSQL、Docker 官方资料。

## 结论

建议先补齐数据生命周期和运维，再整理轻量知识入口，暂时保留 SQLite。当前没有足够证据支持立即迁移 PostgreSQL 或建设独立向量知识库。

| 事项 | 判断 | 优先级 |
| --- | --- | --- |
| 清理保护历史证据 | 已发现两项可复现问题，先修 | P0 |
| 维护任务独立于业务暂停 | 当前暂停会跳过清理和备份，需要调整 | P1 |
| 日志和各类数据分开保留 | 已有部分清理，覆盖与监控需要补齐 | P1 |
| 异地备份、恢复演练 | 当前备份和主库位于同一数据卷 | P1 |
| 给开发 AI 的项目知识入口 | 值得做，使用仓库内 Markdown 和简短 AGENTS.md | P1 |
| 给运行中的 AI 增加领域知识 | 按实际任务逐步补充，接入现有记忆和提示组装 | P2 |
| PostgreSQL | 有明确并发或部署需求后再迁移 | 条件触发 |
| 独立 Wiki 服务、向量数据库 | 当前缺少必要性证据 | 暂缓 |

这里的 P0 表示可能导致维护失败或学习数据失真，应先处理；不代表已经观察到生产事故。

## 评估边界

- 项目定位为单用户、多账号的内容工具；Compose 中是单应用容器，使用本地数据卷。
- 当前工作区未见生产数据库，未读取线上数据库、磁盘占用、实际日志速率或慢查询。因此不能断言线上数据库已经过大、发生锁竞争，或 AI 记忆实际有多少条。
- 本机 Node 为 18，项目要求 Node >=24，现有 node_modules 中关键包目录为空，未能执行 TypeScript 测试。下述两项复现使用 Python SQLite 3.46.1，在内存数据库中执行项目原始建表语句和相关 SQL；不是完整 Node 运行时验证。
- 本次只形成评估文档，没有修改业务逻辑、执行生产清理或迁移数据库。

## AI 知识库：先明确使用者

### 给开发和维护项目的 AI

值得建设轻量入口。现有 README 和 docs 已经记录不少设计背景，但当前仓库没有项目级 AGENTS.md，且文档存在状态混杂：`docs/体系与路线图.md` 第 76 行仍说大脑碰不到假设登记表、参数和长文，后面的“已完成”又记载了相应接入。

建议用以下几份内容组织现有资料，无需另部署 Wiki：

- 简短 AGENTS.md：项目定位、关键入口、验证命令、不能破坏的业务约束，并链接详细文档。
- 架构与数据流：采集、起草、事实校验、审核、发布、效果回抓、实验和记忆之间的关系。
- 数据字典与保留策略：各表用途、关联、可否重建、删除条件、依赖的统计窗口。
- 运维手册：部署、备份、恢复、暂停、发布结果不确定时的排查。
- 决策记录：为什么使用 SQLite、什么条件下迁移、AI 可修改的边界。

现状、历史观察、未来计划应明确标注；测试数量、样本量、账号表现需要附日期或从工具读取，避免静态数字长期冒充现状。知识入口要链接到源码，避免复制大段实现后失去同步。

### 给运行中的 AI 大脑与写作流程

项目已具备基础知识与记忆能力：`brain_memory` 有来源、置信度、证据数、有效期和替代历史；`src/brain/memory.ts` 负责召回，`src/brain/author.ts` 组装写作简报。召回采用中文双字片段和标签相关性等规则，目前没有向量检索。

在这些基础上补充更划算：

- 稳定知识：账号定位、指标定义、内容边界、领域概念；带来源、版本、复查日期及适用账号或标签。
- 经验结论：继续保留证据数、置信度、反例、失效条件；“未验证假设”不能成为确定知识。
- 实时事实：继续从行情及事实台账获取，Wiki 中的旧价格和旧费率不能进入当期事实来源。
- 检索结果：按任务选择少量内容，记录引用的知识版本，便于回查某条建议为何产生。

新增 Markdown 文件不会自动进入线上模型上下文。需要在 `brief` / `buildSnapshot` 等实际提示组装入口接入，明确哪些任务会读取哪些内容。

先收集一组真实任务验证“应召回什么、实际召回什么”。出现现有规则检索稳定遗漏相关知识、长文档难定位或上下文开销过高时，再比较全文检索与语义检索；向量能力也不要求先迁移整个业务数据库。

## 数据清理：已有机制存在，但需要修正

### 已有能力

- `src/lifecycle.ts`：按类目让素材、草稿失效；默认保留素材和事件 14 天；清理超过 72 小时且没有引用的图表；榜单样本窗口为 7 天。
- `src/hot/pool.ts`：采样流程另按 `sampleRetentionHours` 清理热度样本，默认 48 小时；生命周期清理另有 14 天兜底。
- `src/brain/memory.ts`：将到期记忆标为 expired，召回时排除。
- `src/backup.ts`：到期后使用 `VACUUM INTO` 备份，默认保留 7 份。实际触发是 tick 检查距上次备份是否满 20 小时，并非固定午夜任务。

### P0：被帖子引用的旧素材会导致清理失败

`src/lifecycle.ts:154` 按 `collected_at` 无条件删除旧素材；`posts.material_id` 外键引用 `materials.id`，且 `Store.open()` 开启外键约束。

只要保留期外有素材仍被任意状态的帖子引用，就会触发 `FOREIGN KEY constraint failed`。该异常发生在构造清理报告的中途，后续样本、事件、图表和榜单清理不会继续执行。daemon 捕获异常后继续业务，不会自动修复这项维护失败。此前的失效标记操作也不会自动回滚。

建议保留仍有业务引用的素材，只清理未引用旧素材；先清点短帖和长文等全部引用关系。需要更长历史时，可将最小事实证据随内容归档，再按明确契约处理原始数据。不要通过关闭外键或级联删除已发布帖子解决。

验收应包含：保留期外被引用素材安全保留、未引用素材删除、其他清理仍能完成、历史归因和事实溯源可用。

### P0：清掉榜单缓存会抹去历史上榜事实

`src/rank/observations.ts:54` 每次重算先将 `surfaced` 设为 0，再查询当前 `square_board_samples`；upsert 会覆盖已有分发记录。榜单样本超过 7 天被清理后，再计算同一帖子，会把曾经的上榜结果覆盖成未上榜。

临时 SQL 复现结果：

```text
Referenced-material cleanup: FOREIGN KEY constraint failed
Historical board evidence before pruning: (1, 'test-board')
Historical board evidence after pruning:  (0, None)
```

建议把“曾经上榜、首次发现时间、榜单类型”作为独立历史事实持久保存，缓存到期不代表历史事实被推翻。榜单比较池仍可保留 7 天窗口。不要将历史改为需要永久保留整个缓存才能解释。

验收应包含：删除过期比较池并重算后，历史上榜记录保持；真正从未观察到上榜的帖子不会被误标为上榜。

### 建议的初始保留策略

下表为建议起点，需要结合线上增长量和业务分析窗口调整，不能直接作为全表删除规则。

| 数据 | 建议 | 关键条件 |
| --- | --- | --- |
| 行情热度原始样本 | 48 小时，必要时少量日汇总 | 覆盖成熟判定、冷却及排查窗口 |
| 未引用且已失效素材 | 14 天 | 先排除所有业务引用 |
| 榜单比较缓存 | 7 天 | 上榜历史事实已独立持久化 |
| 常规运行事件 | 14–30 天 | 先确认消费者窗口；例如 snapshot 有 30 天事件查询 |
| 错误和异常诊断明细 | 30–90 天 | 重要故障另留摘要；未关闭告警保留 |
| AI 调用回复和诊断详情 | 30–90 天 | 有报告或决策引用的证据先归档 |
| AI 用量汇总 | 约 1 年 | 用实际 token usage；目前 brain_calls 主要记录字符数 |
| 已拒绝或作废草稿 | 30–90 天后归档或删除 | 检查子表、复盘引用和图表引用 |
| 已发布内容、效果检查点、实验臂、转化数据 | 长期保存，后续按年归档 | 这是学习和归因资产 |
| 生效记忆与决策变更历史 | 长期保存；失效版本可归档 | 保留证据链和替代关系 |
| 本地备份 | 保留 7 份作为起点 | 另有异地备份和恢复验证 |

`brain_calls`、`brain_alarms`、`brain_reports`、`lane_leases`、历史草稿等目前没有看到统一的归档/清理策略。它们增长不一定都快，需要按行数、占用和增长率决定；不能因为没有清理就立即批量删除。

### 调度、容器日志与磁盘

业务暂停在 `src/daemon.ts:88` 提前返回，清理与备份位于其后；关闭 autoRun 时也不会自动执行 tick。建议把维护任务从业务发布开关中分离，使用独立定时入口或维护循环，且与现有任务互斥，避免重复维护。

Compose 未显式配置容器日志轮转；宿主机是否已配置尚未验证。Docker 默认 json-file 不自动轮转，可在 Compose 明确使用 local 驱动或配置大小和文件数上限。[Docker 官方说明](https://docs.docker.com/engine/logging/configure/)

维护结果应记录：最近成功时间、各类删除/跳过数量、耗时和错误，并在持续失败时报警。补充数据库、WAL、图表、备份、容器日志及剩余磁盘的占用监控。

SQLite 删除行通常留下可复用空页，文件不会必然立即缩小；`VACUUM INTO` 只压缩生成的备份，不改变主库。根据空闲页比例和磁盘压力安排维护窗口，避免每轮都全库 VACUUM。[SQLite 官方说明](https://www.sqlite.org/lang_vacuum.html)

## PostgreSQL：当前暂缓，明确迁移触发条件

当前是单用户、单应用容器、定时采集与发布，SQLite 已启用 WAL。源码和配置没有证明存在多机器写库需求或持续写锁瓶颈。SQLite 官方也将本机存储、低写入并发视为适合场景。[SQLite 选型说明](https://www.sqlite.org/whentouse.html)

下列需求出现时重新评估 PostgreSQL：

- 采集、写作、发布、分析需要拆成多个并发写库的独立服务，或跨机器运行。
- 需要多个应用副本、高可用、集中数据库管理或更严格的恢复能力。
- 指标证明写锁等待、同步重查询或维护操作持续影响请求和调度，完成索引、事务和查询优化后仍不满足目标。

PostgreSQL 提供 MVCC、行锁和应用级 advisory lock 等并发工具，但业务仍须正确实现任务认领和幂等。[PostgreSQL 并发控制说明](https://www.postgresql.org/docs/current/mvcc-intro.html)

迁移不只是替换连接地址：当前 `better-sqlite3` 接口同步执行，业务模块普遍直接访问 `store.db.prepare()`，同时存在 SQLite 专有语法、JSON 函数、PRAGMA 和备份实现。迁移需处理异步调用链、SQL 差异、迁移版本、数据校验、部署、切换和回滚；也不会自动解决上述保留策略问题。

现在可先做的准备：为数据库变更建立有版本的迁移记录，逐步把新增的关键查询集中到明确的数据访问方法，收集性能指标。无需为了未来可能迁移就立即重写整个数据层或引入 ORM。

## 其他应一并处理的工程事项

- 备份与恢复：主库、图表和备份都在同一数据卷，同卷备份无法覆盖整机或卷丢失。增加异地副本，定期恢复到隔离环境，检查完整性和关键业务数据。备份包含凭据，权限和访问范围应与主库一致。
- 任务互斥：面板 `running` 标志仅保护单进程；同时启动 CLI daemon 或未来多副本时，仍需数据库级租约和发布幂等。换数据库不会自动消除重复调度。
- 查询与索引：events 当前无专门索引，而代码按时间和种类读取。用真实数据和查询计划判断是否加 `(kind, at)` 或时间索引；删除策略也需要合适索引，避免长期同步扫描阻塞面板。
- 变更验证：优先增加能覆盖“被引用旧素材”和“榜单清理后重算”的回归测试，并验证暂停时仍执行维护。现有生命周期测试没有覆盖这两项组合条件。

## 建议落地顺序

1. 修复两项已经 SQL 复现的数据问题，补针对性回归验证。
2. 盘点生产数据体积、表增长、备份状态与容器日志配置；建立各类保留规则。
3. 让维护独立于业务暂停，补清理结果监控、日志轮转、异地备份和恢复演练。
4. 整理项目知识入口，修正文档状态冲突，再按实际 AI 任务增加领域知识召回。
5. 根据并发、部署及恢复需求决定是否迁移 PostgreSQL，根据检索效果决定是否增加语义检索。
