# AI 调用可靠性与双模型评审方案

2026-10-22；依据运行数据库、当前源码及 OpenAI 官方文档。升级 #8 已上线并在面板标记完成。本文保留故障调查与评估方案；调用恢复、独立连接配置和周报单轮审查已实现，实际范围如下。历史失败数字来自实施前窗口，不代表新版本效果。

## 当前实现与配置方法

「AI 大脑」中主模型和第二模型各有独立的协议、Base URL、Key、模型名、拉取模型列表和测试按钮。保留原主模型配置；第二模型初始无 Key、无模型名，备用和审查开关默认关闭。Claude 使用 Anthropic 协议，OpenAI 或兼容中转使用 OpenAI 协议；实际模型名以通道支持列表为准。Base URL 填 API 根地址，不能重复填写 `/messages` 或 `/chat/completions`。填写第二套连接、保存、单独测试通过后，再按需打开两个开关；测试不会借助备用掩盖所测通道的失败。

- **请求恢复：** 主模型每轮最多 2 次尝试（包括参数兼容纠正），备用最多 1 次；超时、HTML、鉴权、配额错误不在同一连接即时重试。临时限流和网关/网络错误有限退避，遵守 Retry-After。每轮业务调用总时限反思/哨兵 120 秒、周报 180 秒，并为备用预留时间；周报审查另限 1 次、120 秒。主模型与备用都失败才记最终失败。
- **持久化补跑：** 反思、哨兵和周报最多执行 3 轮，失败后最早 5 分钟、再 15 分钟补跑，实际取决于自动循环时间。租约 10 分钟，重启可恢复；有效期反思 20 小时、哨兵 6 小时、周报 3 天。哨兵重查当前警报条件，已消失则取消。相同周周期周报幂等，连点不会重复生成。补跑也受预算控制。
- **预算与日志：** 滚动 24 小时默认最多 40 次 HTTP 尝试、200000 token；包含测试、备用和审查。记录实际 usage、状态、错误类别、请求路径和 request ID。缺失 usage 时保守预留输入 UTF-8 字节数加最大输出；不推算美元费用。页面显示近 24 小时/7 天业务结果、历史缺少尝试日志的数量，以及尝试和补跑详情。
- **独立审查：** 仅周报使用第二模型审一轮，引用相同快照字段；程序检查路径和值精确一致（包括 null 与零）。反对、证据不足、引用不符或审查失败保留主报告并暂停建议动作。由备用生成的周报不会再让同一个备用自审；相同接口和型号也不算独立审查。审查支持仍需人工批准、通过原有闸门。字段核对不能证明推理正确。

备用只覆盖 AI 大脑任务，帖子/长文润色仍使用主连接。两个模型共用中转时，故障可能相关。尚未实施连接健康熔断、多轮讨论、审查后自动修订；尚未完成真实双模型的历史案例盲评与七天线上效果观察。开关可分别关闭，不声称已证明提升判断或收益。

以下第 1–2 节是实施前调查，第 3–6 节是方案与后续评估依据；与当前机制有差异时，以本节为准。

**建议：优先完善接入校验、失败恢复和独立备用通道；双模型先只在周复盘做一次独立审查实验，通过评估后再决定是否扩大。** 两个模型互相讨论不能修复错误的 API 地址，也不能修复共用中转的上游故障。

## 2. 已有重试机制与缺口

现有机制在 `src/llm/providers.ts`：

- 429、502、503、504，以及被识别的连接错误、非 JSON 响应：固定等 1.5 秒，再尝试一次。
- 明确表示不支持非默认 temperature 的 400：移除该字段再调用，并在进程内按模型名缓存；其他 400 不这样处理。
- 超时不自动重试。当前单次超时为 `30 秒 + min(maxTokens, 4096) × 40 毫秒`：反思 58 秒、哨兵 78 秒、周报 130 秒。
- 周报另有调度层补跑：北京时间周日 22 点至周二，每两小时尝试一次，成功报告会阻止同周重复生成。

这些机制并非完整恢复方案：

1. 没有区分限流与余额/配额不足；后者重试没有意义。500 未纳入当前 HTTP 重试集合。
2. 没有遵循 `Retry-After`，没有随机退避和整个任务的总时限。参数兼容重试与网络重试嵌套时，最多可能发起四次 HTTP 请求。
3. HTML 首页与网关临时错误被统一判为可重试，容易把地址问题掩盖成网络问题。
4. 没有独立备用连接。`brainModel` 只覆盖模型名，仍共用主连接的协议、地址和密钥。
5. 日常反思即使模型失败仍更新时间戳，通常要等约 20 小时再反思；哨兵先登记警报，再调用模型，失败后相同警报可能被约 20 小时去重挡住。
6. 只有最终成功/失败，没有 attempts、首次成功率、重试挽救率、备用挽救率、token usage 或准确费用。也没有区分“HTTP 成功”和“输出可用”；空文本可能被记为调用成功。

OpenAI 官方建议按状态和错误码区分恢复方式，遵循 `Retry-After`，使用带随机量的指数退避，同时限制次数和总耗时；余额、配额和账单类错误不应盲目重试。[限流与重试](https://developers.openai.com/api/docs/guides/rate-limits)、[错误码](https://developers.openai.com/api/docs/guides/error-codes)。本项目用原生 fetch，并未自动获得官方 SDK 的重试行为。

## 3. 第一阶段：先确保调用可恢复

**A. 接入校验与诊断。** 面板显示协议、脱敏主机、Base URL 路径和最终 API 路径。遇到 HTML 时显示“接口返回网页，请检查地址/协议/网关”，并保存 HTTP 状态、Content-Type、脱敏最终 URL、重定向信息、request ID；不能仅报 JSON 解析错误。区分前端首页、登录页与网关错误页；仅凭 HTML 内容也不能保证识别根因，保留未知类别。不自动猜测或替换用户的 Base URL。

**B. 分层恢复。** 建议默认每次任务主通道最多两次 HTTP 尝试（含参数兼容纠正），再给备用通道一次机会；所有即时尝试合计最多三次。暂定任务总时限：日常反思 120 秒、哨兵 120 秒、周报 180 秒，按实际延迟再调整。发起新尝试前必须检查剩余时间，不能把单次超时重复累加。

| 情况 | 恢复策略 |
| --- | --- |
| 临时限流、500/502/503/504、已识别连接中断 | 有限重试；遵循 Retry-After，否则指数退避加随机量 |
| 401/403、无效模型、普通参数错误、余额/配额不足 | 主通道停止盲重试，明确提示修配置；仅在预先配置的备用通道适用时降级 |
| 200 返回首页/登录页 | 主通道停止同地址重试，提示接入异常；可使用预先配置的备用通道完成任务 |
| 请求超时 | 不立即在同通道重复长等待；在总时限允许时降级，否则登记延后重跑；提示可能产生上游费用 |
| 空结果、必需结构缺失、引用不存在的快照字段 | 标为输出不可用，与传输失败分开；修正或降级也占同一尝试预算 |

若 `Retry-After` 超出剩余时限，登记延后执行，不提前重发。兼容性能力缓存按连接与模型区分，避免不同中转的同名模型互相污染。

**C. 任务与尝试分开登记。** 增加逻辑任务 `brain_jobs` 与传输尝试 `brain_attempts`：任务 ID、purpose、快照标识、状态、下次重跑时间、过期时间；尝试记录连接 ID、角色、状态/错误码、耗时、usage、request ID、脱敏路由。一个任务最终只有一份生效结果。按逻辑任务执行原有唤醒上限，同时增加总尝试与 token 预算，避免重试绕过费用限制。凭据不进入日志。

**D. 补跑不受警报去重阻挡。** 告警是否重复通知与分析任务是否完成分别管理。日常反思、哨兵分析失败后保留待重跑任务，建议 5 分钟后再排队，随后 15 分钟、30 分钟；延后重跑暂定最多两轮，并受全日预算约束。持久化队列支持重启恢复、任务租约和结果幂等；已有任务成功则取消后续尝试。市场状态改变或任务过期时重建快照并留下关联，不拿过期事实自动实施新动作。周报继续按已有周窗口补跑，并统一登记任务状态。

**E. 面板区分历史与当前。** 展示近 24 小时/7 天、版本或配置变更后的统计，拆分业务调用与手工测试；显示首试成功、重试后成功、备用成功、最终失败和输出不可用。历史失败保留，不能通过清零制造“恢复”。

## 4. 第二阶段：独立备用通道

增加连接配置：`provider / baseUrl / model / secretRef`，主连接和备用连接独立保存。建议优先选择故障来源独立的两条通道；如果 Claude 与 OpenAI 型号都经同一个中转，仍可能同时受账号池、DNS、限流和网关故障影响。

备用切换只用于已定义的可恢复任务，必须在记录中标出实际连接、模型和降级原因，不能静默改变判断来源。连续故障可暂时熔断该连接并定期探测恢复；不改变内容发布的既有熔断规则。两个模型是否谁主谁备由本系统样本评估决定，不能仅凭品牌推断优劣。

## 5. 是否需要 Claude 与 OpenAI 讨论

| 方案 | 能解决什么 | 新增代价 | 建议 |
| --- | --- | --- | --- |
| 单模型 + 完整恢复 | 调用不稳定、失败后任务丢失 | 少量重试与状态管理 | 优先实施 |
| 主模型 + 独立备用 | 一条通道不可用时继续完成 | 第二套连接与有限降级费用 | 推荐 |
| 主模型提案 + 另一个模型独立审查一次 | 统计口径误读、证据缺失、建议不成立 | 多一次审查请求、延迟与评估 | 周报先试点 |
| 两模型反复辩论、多轮裁判 | 可能拓展分析角度，尚无本项目收益证据 | 多轮输入增长、循环、错误相互强化、结果难归因 | 暂不实施 |

双模型不会自动得到正确答案。它们可能共享盲点，也可能被同一份缺字段的快照误导；升级 #8 必须补数据口径，换模型不能替代这项工作。OpenAI 官方同样建议由评估结果决定是否采用多代理架构，而不是先增加编排复杂度。[评估最佳实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。

试点流程：

1. 固定一份快照和字段定义；主模型提出一条建议及证据、反例和到期日。
2. 第二模型先根据同一快照独立提取关键事实，再检查提案，输出“支持/反对/证据不足”、具体字段及异议。限制一轮，避免反复说服。
3. 程序核对引用字段、样本量、口径与动作范围；两模型一致也不能绕过这些检查。
4. 周报呈现提案与异议；遇到关键分歧维持观察并交操作者审阅，不靠多数票自动改参数。
5. 审查模型不可用时，主报告仍可保存并清楚标注“未完成独立审查”。不把依赖两个请求同时成功作为整份周报可用的前提。

初期只覆盖周报，日常反思和哨兵不默认双调用。必要时主模型依据审查意见修改一次；这第三次质量调用必须显式计入预算，不能隐含在“讨论”里。

## 6. 成本、验收与实施范围

当前数据库只存字符数，不存真实 token usage 和中转账单，无法给出可信的美元/月估算。先记录 usage 并用实际通道计价；无法取得价格时显示费用未知。

相对调用量可先估：普通任务保持一次；备用只在故障时触发；周报独立审查从一次变两次生成请求，若加一次修订则为三次，费用不一定按次数等比，因为输入长度、输出长度和模型单价不同。串行审查会增加周报等待时间。设置单任务与每日预算，不默认每个请求都双模型。

**可靠性验收：** 注入配置错误、429 限流与配额不足、500/502/503、超时、HTML、空输出、备用失败、重启等情况；验证重试类别、总次数、总时限、凭据脱敏、补跑恢复、旧告警不重复通知、报告与动作幂等。线上观察至少七天且达到至少 30 个业务任务，不为凑样本额外生成付费请求；用新旧窗口分开展示最终可用率、延迟和预算消耗。

**双模型验收：** 先用能取得的历史快照构建 20–30 个案例（不足则继续积累），覆盖新旧口径混合、样本不足、零与未知混淆、重复升级和无证据提案。比较单模型与独立审查后结果，由人工按匿名结果核对具体错误。记录新增有效纠错、误杀好建议、无依据主张、人工审阅时间、耗时和费用；不能仅用“两个模型一致”评价成功。可暂设保留门槛：严重证据误读更少，未新增严重错误，且成本与审阅负担在事先设定预算内。小样本仅作探索，不能据此声称统计显著或提升发帖收益。

实施顺序与粗估：接入诊断/尝试日志/有界重试约 1–2 个开发日；持久化补跑、独立备用、面板与故障测试约 2–3 日；周报单轮审查与离线对比约 1–2 日，另需线上积累样本。此为工程估算，取决于现有配置页与数据库迁移工作量。

拟修改位置：`src/llm/providers.ts`（分类与预算）、`src/brain/brain.ts`（任务与尝试登记）、`src/db/index.ts`（迁移）、`src/config.ts` / `src/secrets.ts`（独立连接）、`src/brain/sentinel.ts` / `src/brain/author.ts` / `src/brain/weekly.ts` / `src/daemon.ts`（调度与幂等）、`src/server/brainRoutes.ts` / `src/server/public/brain.js`（状态呈现与连接诊断）。双模型试点以开关控制，可独立关闭。
